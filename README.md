# aura-fx

Aura 决定下不下单，ForexConnect 负责把单子送到 FXCM Demo。本仓库平时用 Aura nightly。这一版用的是自编 main `4f2e40838`，因为需要的修复还没出 nightly，见「安装」。

决策在 Aura 里：三套规则放进 `std/portfolio`，`std/algo-select` 的 kNN 按最近 16 根的斜率和来回次数选一套。换规则走 `std/hot-strategy`，进程不重启。经纪商接口是 Python。两边用同一份成交规则对账，对不上就说明管道没通。

这不是收益承诺。行情是一段写死的 EUR/USD 夹具，用来把管道和选择器跑通。

## 安装

Linux x86_64 或 arm64，nightly 即可：

```sh
curl -fsSL https://raw.githubusercontent.com/cybrid-systems/aura/main/install.sh | sh
export PATH="$HOME/.local/bin:$PATH"
```

本机测过的二进制是自编的 Aura main `4f2e40838`（`aura dev (4f2e408384cbb0960408eed023954e0418e0b39b)`），还没有对应的 nightly。`scripts/*.sh` 优先用 PATH 上的 `aura`，找不到才用 `~/.local/bin`。

所需最低版本：main `3f994c2c3`（aura#5303 的修复，rebind 类型门不再误拒「条件里比较参数、分支返回该参数」的提案）。建议用 `284f6b9e2` 及以后（aura#5304：循环里调用函数快了约 20 倍，冻结验证 v2 和 P1/P3 跑得更快）。还要包含以下修复：
- `4f7ad2c29`（#5302）
- `c2cf0b0a5`（#5301）
- `4062afdd2`（#5294）
- `db235e11c`（#5300）
- `8b1db8930`（#5297）
- `4c61d0eb7`（#5298）
- `d3f57ba46`（#5299）

nightly `6b84c78b` 也能跑通 `EVOLVE_OK` / `PIPE_OK`，但 P5 提案多数会被类型门拒掉，heal 之后订单记的版本号也不对。等出了包含 `3f994c2c3` 的 nightly，直接用 nightly 即可。

自编方法（本机没有 docker，所以把 `ghcr.io/cybrid-systems/aura-ci:v0.1.1` 的 amd64 层解到一个目录里，chroot 进去编译）：

```sh
cmake --preset release && ninja -C build -j8 aura
scripts/tools/bundle.sh build      # 打包，自带 glibc 2.44，宿主 glibc 不影响
tar -xzf dist/aura-<commit>-linux-x86_64.tar.gz && export PATH="$PWD/aura-<commit>-linux-x86_64/bin:$PATH"
```

## 跑通

```sh
bash scripts/pipe.sh
```

脚本做四件事：Aura 写出 `out/session.json`，打印组合差距，热替换一条规则再 heal 回去，然后 Python 用同一条半点差把 63 笔 `OM` 单重放一遍。Aura 的盈亏和 Python 的盈亏必须一致，最后一行是 `PIPE_OK`。

Demo 登录不在这个脚本里。账号放在 `.env`（从 `.env.example` 复制），`.env` 不进 git。

forexconnect 只有 cp35–cp37 的 manylinux x86_64 轮子，要用 Python 3.7（例如 conda-forge 的 `python=3.7`），再装 `forexconnect "numpy<1.22" "pandas<1.4"`。`FXCM_URL` 必须是 `https://www.fxcorporate.com/Hosts.jsp`：走 http 时 Hosts.jsp 返回 500，登录报 ORA-499。

冻结验证（见「冻结验证 frozen-v1」和「冻结验证 v2」）：

```sh
bash scripts/frozen2.sh    # v2：真实小时线，先校验 frozen/v2.sha256，最后一行 FZ2_OK（约 40 分钟）
bash scripts/frozen.sh     # 先校验 frozen/v1.sha256；缺 ECB 数据时用 scripts/fetch-ecb.py 下载；最后一行 FZ_OK
```

```sh
python3 bridge/fc_adapter.py probe    # 看本机能不能加载 forexconnect
python3 bridge/fc_adapter.py login    # 只读余额和 EUR/USD，不下单
```

`login` 拒绝 `FXCM_CONNECTION=Real`。`live` 还会再要 `FXCM_LIVE=1`，并且会把夹具里的单子真正送进 Demo。纸面对账通过之前不要加这个开关。

Demo 账户是对冲模式（`maintenance_type=Y`），反向开仓会变成锁仓。`live` 按净持仓下单：先用 `TRUE_MARKET_CLOSE` + `TRADE_ID` 平掉反向仓位（先开先平），剩下的再用 `TRUE_MARKET_OPEN` 开。

```sh
python3 bridge/fc_adapter.py live --offline              # 不登录，从空仓打印每笔的平/开计划
python3 bridge/fc_adapter.py live --dry-run              # 登录读当前持仓，打印计划，一笔不发
FXCM_LIVE=1 python3 bridge/fc_adapter.py live --max 1    # 先试 1 笔
FXCM_LIVE=1 python3 bridge/fc_adapter.py live --skip 1 --all   # 再跑剩下 62 笔
```

发单必须带 `--max N` 或 `--all`。休市时（纽约时间周五 17:00 到周日 17:15，约北京时间周六 06:00 到周一 06:15）FXCM 拒单，`live` 看到报价 `trading_status` 不是 `O`，或报价时间超过 5 分钟没动，就打印 `MARKET_CLOSED`，不发单。周六实测 Demo 报价仍显示 `trading_status=O`，只有报价时间停在周五收盘，所以要看报价时间。某一笔被拒或没成交就停在那一笔，并打印已完成几笔。

登录超时（`Wait timeout exceeded`）会换一个新会话重试，最多 3 次。这个错误说明会话在 SDK 写死的 30 秒内没到 `CONNECTED`，不是密码错（密码错会直接报 FXCM 的原因，不重试）。在本机上，进程里第一个会话要约 72 秒才连上，登出后第二次一般就能连上。三次都失败时会打印 Hosts.jsp 给出的 Demo 交易服务器地址和探测结果。

## 演化：P1–P5

```sh
bash scripts/evolve.sh
```

脚本依次跑 P1（跑两遍，`out/p1.json` 必须逐字节相同）、P2、两份对抗会话的适配器风控、P3、P4、对 `out/live-session.json` 做纸面对账和 `live --offline`，有 `MINIMAX_API_KEY` 时再跑 P5，最后一行是 `EVOLVE_OK`。每一步打印墙钟、CPU 时间、等效核数和子进程峰值内存。不登录 FXCM，不发单。密钥只从环境变量读，不打印。

以下数字都是本机（x86_64，8 核，15.6 GB，自编 main `a407ecc12`）跑出来的。机器上另有一个进程常驻约 2 个核，墙钟会有波动。行情是种子生成的夹具，不是历史行情。这不是收益承诺。

### 夹具与指标

`lib/tapes.aura` 用 `evo:rng` 按种子生成磁带：8 段、每段 40 根，段落在上行、区间、下行三种行情里按 0.6 的概率延续。种子 7 生成 6 条磁带，每条 7 个窗口。`lib/metrics.aura` 有 Sharpe、最大回撤和 Bailey–López de Prado 的 deflated Sharpe（按试验次数扣掉多重比较带来的期望最大 Sharpe）。

aura#5290 修好之后，相邻种子的随机流不再相关，`tape-rng` 去掉了自己的混合和预热，直接用 `(evo:rng seed tape segment)`。磁带因此和旧版不同：种子 7 这组趋势段更多（有一条 8 段全是上行），上线规则的样本外合计从 1221.13 变成 2274.35。下面新旧数字不能直接比大小。

### P1 参数演化 + 样本外门禁

前进式三折：用窗口 1..k-1 训练，在窗口 k 测试，k = 5、6、7，共 18 个样本外窗口。每种搜索每折 64 次评估、种群 8。KEEP 要同时满足：`tune:gate` 在 α=0.05 下通过（对上线规则做配对 t 检验），并且 deflated Sharpe > 0。

提交用的搜索事先定为 race：第 k 折用哪种算法，由 `tune:race` 在第 k-2、k-1 两折的测试窗口上决定（每种算法在 j 之前的窗口上拟合、在窗口 j 上打分，6 条磁带 × 2 折 = 12 个配对样本）。第 k 折的测试窗口不参与选择。选出的算法在第 k 折的参数再拿去测窗口 k。deflated Sharpe 按三种算法在 3..7 五折里打过分的所有候选计数（960 次）。

| 搜索 | 样本外合计 | t / 临界值 | deflated | DSR | 试验数 | 门禁 |
|---|---:|---:|---:|---:|---:|---|
| 上线规则 `(8 2.5 6.0 8)` | 2274.35 | | | | | |
| es | 2347.08 | 2.37 / 1.725 | 2.00 | 1.000 | 192 | KEEP |
| pso | 2375.86 | 2.34 / 1.725 | 1.29 | 0.981 | 192 | KEEP |
| abc | 2276.41 | 0.10 / 1.725 | 2.28 | 1.000 | 192 | ROLLBACK |
| **race（提交）** | 2347.08 | 2.37 / 1.725 | 1.42 | 0.994 | 960 | **KEEP** |

race 三折都选了 es。第 7 折参数 `(rule-switch 7 3.84 2.0 10)` 在子 workspace 里试验通过，`evo:commit!` 经 `hot-strategy:swap!` 上线，后面 P2–P5 都从它启动。两次运行的 `out/p1.json` 相同。

这个 KEEP 不稳。同样的代码换夹具再跑（不进 `evolve.sh`）：

| 夹具 | 上线规则 | es | pso | abc | race |
|---|---:|---:|---:|---:|---:|
| 种子 7（本版磁带） | 2274.35 | 2347.08 KEEP | 2375.86 KEEP | 2276.41 | 2347.08 KEEP |
| 种子 7（旧的混合种子磁带） | 1081.70 | 1543.60 | 1323.50 | 1230.87 | 1367.14 |
| 种子 11 | 1269.25 | 1461.65 | 1533.51 | 1332.19 | 1457.59 |
| 种子 23 | 1137.89 | 1676.59 KEEP | 1493.70 | 1320.85 | 1450.77 |

四组里 race 只过了一组，es 过了两组，pso 过了一组。race 多付的试验数让 deflated Sharpe 更难过，在这几组上也没有比单用 es 更好。所以「换成 PSO」或「race 选算法」都没有显示出稳定优势。race 留作提交方式，是因为它事先定好、不偷看测试窗口，不是因为它更强。

P1 现在要跑五折（3..7，前两折只给 race 用），墙钟从约 55 s 涨到 66–84 s，等效 5.9 核。

### P2 风控不变量

最大持仓 10000、最大回撤 150、每 40 根最多 24 笔，写成 workspace 里的 `risk-*` define，作为 `evo:search` 的 constraints，提交前过 `evo:feasible?`。`risk-*` 在提案器的 protected 列表里。

| 对抗候选 | 拦下它的 | 日志 |
|---|---|---|
| oversize-5 / oversize-2 | infeasible: max-pos（也超回撤） | ROLLBACK |
| always-short / inverted | infeasible: max-dd | ROLLBACK |
| flip-every-bar / flip-2-of-3 | infeasible: order-rate | ROLLBACK |
| edit-max-pos / bundle-max-dd | `prop:check-proposal`：protected | ROLLBACK |
| set-in-body / eval-in-body | `prop:check-proposal`：protected | ROLLBACK |

10/10 被拒，10/10 有 ROLLBACK 记录，上线规则和 `risk-*` 都没变。aura#5291 修好后，函数体里对 `risk-*` 的 `set!` / `eval` 由 `prop:check-proposal` 自己拦下（旧版它会放行）。本仓库的函数体守卫保留，作为第二道：它对任何名字的 `set!`、`eval`、`mutate`、`getenv`、`write-file` 都拒，protected 列表管不到这些。Python 适配器有自己的一套检查（持仓 10000、单笔 20000、每 40 根 32 笔），`paper` 遇到超仓会话和翻手会话都打印 `RISK_BLOCKED` 并返回 3。

### P3 并行候选与在线选择

任务集：训练窗口 1..4（24 个），测试窗口 5..7（18 个），`meta:disjoint?` 为真，故意混入一个测试窗口时能查出来。

| 项目 | 结果 |
|---|---|
| nsga2（盈亏 vs 回撤，种群 16，128 次评估） | 串行 12.0 s，fiber 并行 8.7–11.7 s，结果相同 |
| 前沿 | 超体积 2860560 → 3282859，单调不降 |
| MAP-Elites（斜率 4 格 × 来回次数 2 格） | 填满 5/8 格，加入 5 个新成员，组合共 10 个 |
| gap-closure（留一法） | 原 3 成员 0.65；10 成员 kNN k=1 -5.68，k=3 -1.48，tree -0.43 |
| 样本外：kNN 选择器 | 2318.80，SBS（elite-2-0）2414.93，t=-2.04 |
| 样本外：regime 选择器（`lib/regime.aura`） | 2414.93，与 SBS 相同，t=0 |
| 样本外：事后最优（oracle） | 2430.74 |

验收没过，选择器没有超过 SBS。

`lib/regime.aura` 是这次换上的选择器：用窗口开始前一根的斜率（上/平/下）和来回次数（高/低）分格，切点取训练特征的中位数。默认跑 SBS，某一格里只有在 `tune:gate`（α=0.10，至少 3 个窗口）认为别的成员确实赢过 SBS 时才换，测试窗口收盘后才把它加进格子。结果 18 个窗口一次都没离开 SBS，所以不再输给 SBS（kNN 少 96），但也赢不了。

原因在夹具本身：事后最优只比 SBS 多 15.8（18 个窗口）。10 个成员大多是同一族 `rule-switch`，elite-2-0 几乎在每个窗口都是最好或并列最好；行情在窗口边界上才换段，开窗前的特征反映的是上一段。选择器能拿的空间不到 1%，这组夹具上没有可学的东西。要让选择器有意义，成员得更不一样（不同的规则族），或者特征要有前瞻性，这两样都不是换选择算法能解决的。

aura#5297 修好后，那张单里「读捕获变量」的复现从 1.4 倍变成 8.0 倍，但这里的 NSGA-II 仍然只快 1.4 倍（串行 12.6 s，8 fiber 9.1 s）。回测循环全是浮点运算。单独测，浮点累加的 named let 在 8 fiber 下只快 2.5 倍，每步分配一个 list 的只快 1.7 倍，同样写法的整数循环能快 7.9 倍；而且串行时浮点比整数慢约 13 倍。已建 aura#5302。

### P4 实时回路

磁带 s99-t0（280 根，上行、区间、下行都有）。每根先过前置风控（持仓钳位、频率限制），每笔单子带上特征、成员、规则版本、候选 id，写进 `out/live-session.json`，并在 evo 日志里记一条 `ORDER`。

drift 改用 Page-Hinkley（`lib/drift.aura`），看的是上线规则每根的盈亏是否开始持续低于自己的均值。δ、λ 在种子 7 的 6 条磁带上标定（网格 δ∈{0,1,2,4} × λ∈{50,…,300}，按「行情换段后 40 根内报警」算命中，取命中减误报最大的一组，平局取报警少的），不看实盘磁带。标定结果 δ=0、λ=150。报警后由 regime 选择器按当前特征挑成员，先 `evo:trial` 最近 80 根，过门禁才 `hot-strategy:swap!`。如果报警时在跑的规则不是过过门禁的成员（比如注入的那条），直接 `hot-strategy:heal!` 回上一版。

| 项目 | 旧触发（kNN `select:drift?`） | 新触发（Page-Hinkley） |
|---|---:|---:|
| 报漂移的根数 | 264 / 280 | 1 次报警 |
| 尝试替换 | 6 次（1 次上线，5 次被拒） | 0 次 |
| 第 200 根注入反向规则后 | 第 221 根被一次普通替换换掉，没有走 heal | 第 225 根报警，同一根 `heal!`，延迟 0 根 |
| 订单 / 盈亏 / 期末持仓 / 最大回撤 | 23 / 611.28 / -10000 / 57.19 | 23 / 584.25 / -10000 / 70.7 |
| `P4_OK` | 否 | 是 |

两列是同一份代码、同一条磁带，只换触发条件。Page-Hinkley 唯一的一次报警就是注入的故障（25 根后发现，回撤 66.95，还没到 75 的 heal 线）。4 次行情换段一次都没报：上线规则在这几次换段时没有亏，所以按这个检测器的定义不算漂移。标定集上 14 次换段也只命中 1 次（λ=50 时命中 3 次、误报 2 次），它是一个「规则在亏」的检测器，不是行情换段检测器。新触发的盈亏比旧的少 27，因为注入的规则多跑了 4 根。

| 其他 | 结果 |
|---|---|
| Python `paper` | 23 笔，盈亏一致，`PIPE_OK` |
| `live --offline` | `DRY_RUN_OK` |

另修了本仓库一个越界：旧代码第 80 根起就可能去取「最近 80 根」窗口，会读到第 1 根之前，现在第 119 根起才尝试替换。

### P5 LLM 提案（离线）

MiniMax-M3.1-Flash，`reasoning_effort=minimal`，`llm:rate-limit-set! 20`。每轮让模型写 3 个 `(define (rule-entry ...))`，同时给出之前提案的训练盈亏。提示里现在写明搜索用的参数范围（n 4..24、trend-pips 0.5..10、fade-pips 2..20、chop-split 2..16）、上线规则（P1 提交后的那条）按行情分的训练盈亏、训练段上斜率和来回次数的 10/50/90 分位。提案只能改 `rule-*`，与 ES 走同一套门禁（`prop:check-proposal`、函数体守卫、子 workspace 试验、风控约束、`tune:gate` + deflated）。两边同样 12 个候选，与上线规则比样本外（2297.29）。

| 方法 | 候选 | KEEP | 不可行 | 训练最好的那个：训练 / 样本外 | t | 用时 |
|---|---:|---:|---:|---:|---:|---:|
| ES | 12 | 0 | 0 | 1891.33 / 2205.93 | -2.94 | 3.6 s |

## v3：降低换手的策略搜索，在没用过的货币对上做最终检验（frozen-v3）

v2 的教训：8 条成员规则交易太频繁，按零售点差在留出段全部亏钱。v3 只用 EUR/USD 训练段（2019–2023）做搜索和选型。最终检验用的是冻结之前从未下载过的 GBP/USD、USD/JPY、AUD/USD（2024-01 至 2026-10），并且只跑一次。v2 的 EUR/USD 留出段已经看过，只作参考。

### 试了什么

- **周期**：把 H1 聚合成 H4（UTC 每 4 小时一根）和 D1（交易日在 22:00 UTC 收盘，周末的小时并入周一），见 `scripts/v3-bars.py`。
- **规则族**（`lib/v3.aura`）：所有阈值都按波动单位（约 20 根的 |收盘变化| EWMA）计，不同货币对之间可以直接套用。
  - **trend**：EMA 快慢线差，带入场阈值、滞后带和最短持有期，外加波动率过滤；
  - **donch**：突破前 N 根高低点，按前 M 根的反向极值出场，带最短持有期和波动率过滤；
  - **tsmom**：L 根收益的符号，只有当 |z| 超过阈值时才交易，每 R 根调一次仓；
  - **meanrev**：按 SMA(n) 的 z 值反向入场，带出场带和最长持有期；当长期趋势太强（4n 的 z 值过大）时不入场。
  - 另外还有一个不交易的 flat 选项：它不参与搜索，只作为选择器的备选。
- **成本**：点差 1.3 点，每笔在中间价上付一半；一手 1 万欧元；以美元计。适应度直接用扣除成本后的日度 Sharpe。
- **搜索**：每个组合（周期 × 规则族 × 算法）在每一折里评估 128 个候选，8 条 fiber 并行。
  - `search:init` 的 es：只最大化训练段年化 Sharpe；
  - `nsga2`：同时优化 Sharpe（最大）、最大回撤（最小）、每年成交手数（最小），从前沿里选 Sharpe > 0 中 calmar 最高的。
- **训练段内部的锚定 walk-forward**：用 2019–2020 搜索、2021 验证；2019–2021 搜索、2022 验证；2019–2022 搜索、2023 验证。最后用 2019–2023 全部重搜一次，得到可以冻结的参数。

  - **「近期赛跑」**（`v3-select.aura`，部署规则，在搜索跑完之前就提交了：`51341bb`）：用 `tune:race` 在已有的验证月份上比较 16 个组合。赢家只有在验证期均值 > 0、且按 16 个组合 deflate 后的 Sharpe > 0 时才交易，否则不交易。

## v4：LLM + 自进化搜索新规则类型，在没用过的四个货币对上做最终检验（frozen-v4）

想回答的问题：把 LLM 和 Aura 自带的自进化（`evo:*`、`search:*`、`pareto:*`、`hh:*`、`hot-strategy:*`）组合起来搜索新的规则类型，在事先不知道结果的前提下，能不能找到赚钱的规则。

搜索、进化和给 LLM 的反馈只用 2019–2023 的训练段。训练段里按验证年 2021 / 2022 / 2023 做锚定 walk-forward。部署规则在搜索之前就提交了（`003f877`）。最终检验用冻结之前从未下载过的 USD/CHF、USD/CAD、NZD/USD、EUR/JPY（Dukascopy 小时线，2024-01 至 2026-10），只跑了一次。EUR/USD（v2 看过）和 GBP/USD、USD/JPY、AUD/USD（v3 看过）只作参考。

### 做法

- **数据**：D1 线（交易日在 22:00 UTC 收盘，周末的小时并入周一）。训练用 EUR/USD、GBP/USD、USD/JPY、AUD/USD 四对，对齐到同一个日历，各 1301 天。每天的特征见 `scripts/v4-prep.py`：
  - 波动单位下的收益 `zret{5,10,20,60,120}`、相对均线 `zsma{10..200}`、通道位置 `dpos{10..120}`、波动比 `vr`、上涨天比例 `up{10,20,60}`、昨日收益 `r1`；
  - **新信息**（都来自公开、不需要凭据的来源）：
    - 美元强弱 `usd{5,20,60}`：四对按美元方向取平均的 z 收益，即跨货币对强弱；
    - 利差 `carry`：BIS WS_CBPOL 政策利率，用上个月的值。
- **成本**：
  - 每成交 1 单位付半个点差；
  - 每晚收付隔夜利息，按 (利差 − 1% 年化加价) 计，周三算 3 晚；
  - 每对 1 万单位，盈亏换算成美元，四对按天相加。
- **规则 DSL**（`lib/v4.aura`）：`(rule EXPR TIN TOUT HOLD)`。
  - EXPR 是表达式树：终端是上面的特征和常数，运算有 `+ - * / min max neg abs sgn clip ifgt`；
  - 节点 ≤ 25、深度 ≤ 6；
  - 得分 > TIN 做多、< −TIN 做空，回到 TOUT 以内平仓，最短持有 HOLD 天。
- **门禁**（每条候选都走一遍，`lib/v4evo.aura`）：
  1. `prop:check-proposal` 加关键词扫描；
  2. `evo:trial`：在子世界线里用 `mutate :rebind` 把规则装成 `rule-score`，逐根重算，结果必须与按列计算的结果一致（误差 1e-6 以内）；
  3. 可行性：每对每年成交 2–30 次，最大回撤 ≤ 4000；
  4. `tune:gate`：在拟合区间的日盈亏上，对当前冠军做配对 t 检验（α 0.05）；
  5. 按本折已有的全部试验 deflate 后仍 > 0；
  6. 最后 `evo:commit!`：KEEP 时经 `hot-strategy:swap!` 换上线规则，否则 ROLLBACK，都写进 evo 日志。
- **三个分支**，每个分支跑 4 折（拟合 2019-04 至验证年前一年，验证年分别是 2021、2022、2023；`full` 折拟合 2019-04 至 2023 年底），共 12 个进程：
  - **gp**：种群 40，15 代。
    - 变异算子有 subtree、point、xover、hoist、param 五种，由 `hh:make` FRRMAB 赌博机按收益分配概率，挖掘策略本身也在演化；
    - 选择用 NSGA-II（`pareto:nd-sort` + `pareto:crowding`，目标是适应度最大、节点数最少，带约束违反）；
    - 每代对最好的个体用 `search:init "es"` 调 TIN / TOUT / HOLD；
    - 适应度 = 训练年化 Sharpe − 0.01 × 超过 10 的节点数。
  - **llm**：MiniMax-M3.1-Flash（`llm:chat`，`reasoning_effort=minimal`，`--grant net`），8 轮，每轮要 4 条规则。
    - 提示里只有拟合年份、23 个单特征探针的训练统计、前 5 名、当前冠军和最近 6 条失败原因，没有 2024 年以后的任何数据；
    - 提示风格有 explore / refine / repair 三种，由第二个赌博机选择，每次切换都经 `hot-strategy:swap!` 换 `rule-miner`。
  - **hybrid**：与 gp 相同，但初始种群和之后每 3 代各调一次 LLM。LLM 的提案既作为种子，也作为一个变异算子注入种群。
- **部署规则**（`v4-select.aura`，搜索前提交）：只有同时满足以下三条才交易 hybrid 的 full 折冠军，否则不交易：
  1. 这个冠军存在；
  2. hybrid 在 2021–2023 验证年上的合计均值 > 0；
  3. 按 3 个分支 deflate 后的 Sharpe > 0。

### 这次碰到的 Aura 问题

- **aura#5309（新建）**：`or` / `and` 的操作数是非尾位置的递归调用，并且递归路径上调用过 std 函数时，返回文件第一个顶层形式的值，或报 `unbound variable: require`。GP 的 DSL 检查改用累加器绕开。
- **aura#5310（新建）**：生产模式下的 CastOp 密度连击门让 `mutate:rebind` 的结果依赖之前的提交历史，同一个函数体先被拒、原样再提交又通过；`AURA_CASTOP_DENSITY_STREAK_GATE` 不生效。在 v4 里，这会让含 `if` 的规则在 `evo:trial` 里随机地 `apply-failed`。现在规则体里的所有运算都改成调用模块函数（`v4o-*`）。
- **aura#5311（新建）**：`vector-map` 对每个元素都 apply 并新建闭包和列表，单个向量时比列表 `map` 慢 8–9 倍。逐列求值因此改用列表。

### 结论

- **还是没有找到在事先不知道结果的前提下、经得起检验的赚钱规则。** 部署规则在搜索之前就写定了，结论是不交易，在新货币对上的结果是 0。
- 如果硬要交易：
  - full-gp 冠军在四对合计上赚了 1664 美元（t 0.72）。但它只在 USD/CHF 和 EUR/JPY 上赚，按 N=6922 deflate 后 DSR 0.002，按 N=3 deflate 后 0.52，都远未达到显著；最近 10 个月在回吐（−1291）。其中约 612 美元来自隔夜利息（不计隔夜利息时为 +1052）。
  - LLM 冠军亏 1987 美元（t −0.84），hybrid 拟合最好的那条亏 679 美元。
- LLM 在这里的作用更像一个「合理先验」：提出的规则可读、能通过 DSL 检查（221 条中 197 条合法），但训练段样本内并不比 GP 好，样本外也没有优势。把它和 GP 放进同一个闭环（hybrid）后，KEEP 数反而比纯 GP 少。
- 门禁很严：t 检验对比冠军，再按已有试验 deflate。317 条进入门禁的候选只 KEEP 了 5 条，各折验证期的冠军大多是不交易。这正是我们想要的：宁可不交易，也不上线靠运气得来的规则。
- 注意：MiniMax 模型在预训练时可能见过 2024 年以后的行情描述，这个泄漏无法排除。好在 LLM 冠军在测试期是亏的。

## v5：5 分钟数据上的在线自适应 vs 固定参数 vs 不交易，以及交易频率到底重不重要（frozen-v5）

起因：用户问交易频率要不要更高，回复是「不用这么高频 适合aura频率的就好」。所以这一版不追求高频，而是系统地回答两个问题：(1) 同一套信号在 M5 / M15 / H1 / H4 换仓时，毛利、成本、净利和交易次数各是多少，瓶颈在信号还是在交易方式；(2) 让 Aura 每 N 天在最近 W 天上重新选参数并热切换（`hot-strategy:swap!` / `heal!`），能不能比固定参数和不交易更好，以及 Aura 能不能跟上这个节奏。

Aura 仍用自编 main `4f2e40838`（`/tmp/aura-main3`）。开工时 origin/main 比它多 22 个提交，全是重构和测试，#5304 / #5307 / #5309 / #5310 / #5311 都还是 OPEN、没有修复，所以没有重编。

### 做法

- **数据**：Dukascopy 逐日 M1 BID（`scripts/v5-fetch.py`，32 线程，原始文件缓存在 `data/raw-dukascopy-m1/`，不入库），聚合成 M5。训练/设计段 EUR/USD、GBP/USD 2019–2023（2019 上半年只作窗口预热，打分从 2019-07-01 开始）；M1 下载很慢（训练段 3130 个文件约 100 分钟，服务器限流、偶有 503），但没有缩减训练年份。最终检验用从没下载过的 EUR/GBP，2024-01-01 至 2026-10-31（另下 2023-06 起的数据作历史窗口）。
- **信号**（`scripts/v5-prep.py`，按列预计算）：96 个配置 = 4 个换仓频率（M5 / M15 / H1 / H4，即每 1 / 3 / 12 / 48 根 5 分钟线才允许改仓）× 3 族（动量 mom、均值回归 mr、突破 brk）× 回看 L ∈ {12, 48, 288, 1440} 根 5 分钟线 × 2 个阈值。在一根线收盘时决定的仓位持有到下一根线。1 万单位，美元记账，交易日在 22:00 UTC 切分。
- **成本**：每交易 1 单位 = 倍数 ×（点差/2 + 每边 0.2 点滑点）；点差 EUR/USD 1.3、GBP/USD 按同一来源换算，EUR/GBP 1.1（FXCM 标准账户公布值，来自 compareforexbrokers 的点差表，**是公布值不是实测**）。隔夜利息用 BIS 政策利率（上月）减 1% 加点，周三 ×3。另跑一份 2 倍成本。
- **在线自适应**（`lib/v5.aura`，Aura 里跑控制循环）：每 N 个交易日用最近 W 天的窗口 Sharpe（前缀和）给 96 个配置打分，再按三种方法之一决定是否切换：
  - `greedy`：直接换成窗口最好的；
  - `gate`：用 `tune:gate`，候选要显著好过当前配置才换；
  - `race`：用 `tune:race`，在前 8 名 + 当前 + 空仓之间，以 5 天为一块做 race。
  - 切换用 `hot-strategy:swap!` 改写工作区里的 `active-config`；如果切换后当前配置亏钱、而上一个好配置这段时间会赚更多，就 `heal!` 回滚。
  - Page-Hinkley 漂移检测（`lib/drift.aura` 的 `ph-step`，delta 0.5、lambda 4.0，未调参）触发时提前做一次决策。
  - 切换成本 = |日末仓位差| × 单位成本，计入净值。每次运行先强制切回空仓。
  - 变体：N ∈ {1, 5, 20} × W ∈ {20, 60, 120} × 3 种方法 = 27 个。
  - 没用 `search:init`（网格是显式枚举的 96 个配置，不需要搜索器生成）；没用 `select:drift?`（它需要特征表，这里用 Page-Hinkley 代替）。
- **部署规则**（`scripts/v5-select.py`，在搜索前随协议提交 `3248b7d`）：
  - v1 = 设计段（2019-07-01 至 2021-12-31）Sharpe 最高的自适应变体；val1 = 它在 2022–2023 的 Sharpe。
  - v* = 全训练段（2019-07 至 2023）Sharpe 最高的自适应变体；f* = 全段最好的固定配置。
  - 试验数 N = 96 个固定 + 27 个自适应 + 3 次冒烟运行 = 126，用全部 126 个 Sharpe 的方差算 SR0。
  - 只有 val1 > 0 且 SR(v*) − SR0 > 0 才交易 v*，否则空仓。最终检验里 v*、f* 和空仓都作 as-if 记录。

- 一次决策（96 个配置打分 + gate/race + 可能的 swap）几十毫秒，单进程每秒约 20 次决策。即使每根 5 分钟线都决策一次（预算 300 秒），也绰绰有余；这里实际是每 N 天一次，Aura 完全跟得上。
- 两个问题：
  1. 每个进程开头会有一次几秒到 13 秒的停顿（训练段 9 个进程各一次，最终检验 1.7 秒和 6 秒），都在加载 CSV 之后不久。用一个纯分配 + 循环的小脚本没能复现，原因没查清，所以没有建单；`gc` 在生产模式下被禁用（#4449），没法手动触发 GC 来验证。

- 没有跑 CI，没有重编 Aura；没连 FXCM，没有实盘或模拟盘下单。

### 结论

- **频率**：从 M5 到 H4，每次交易的毛利都在 0 附近而成本固定约 2 美元，频率越高只是亏得越多。瓶颈在信号，不在交易方式；"适合 Aura 的频率"在这里意味着低频（H4 或按日调整），但低频本身不会凭空产生收益。
- **在线自适应**：只有 `tune:gate` 这种克制的切换方式没有被成本吃掉。在训练段的样本外验证里，它没有赢过固定参数和空仓。最终检验 as-if 1× 成本 +813（t = 1.21，DSR 0），2× 成本 −336，不显著，也经不起成本误差。
- **Aura**：控制面延迟（决策几十毫秒、swap 十几毫秒）远低于任何合理的调整节奏；需要注意 #5312 的累积变慢和开头的停顿。
- **部署**：按事先提交的规则空仓。不建议用这套规则上 Demo 实跑；它至多值得作为观察对象继续纸面跟踪。
